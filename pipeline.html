The DevSecOps Pipeline, Step by Step

Exactly what runs, in order, on every push to main — pulled directly from the two live workflow files.

Stage 1 — CI Build/Lint/Test

File: .github/workflows/ci.yml

Triggers on: push to main, and every pull_request targeting main.

1. Lint Python (app/status-service) runs first

  1. Checkout — clone the commit being tested
  2. Set up Python — Python 3.12
  3. Install ruff
  4. Check for Python sources — skip cleanly if app/ has no .py files yet
  5. Run ruff lint — scoped to app/ only
  6. Note on Haskell/Clash suites — points at the separate cabal test/stack test suites elsewhere in the repo, not run here

2. Python unit tests (status-service)

needs: lint-python — only runs if step 1 passes
  1. Checkout
  2. Set up Python
  3. Check for requirements file
  4. Install dependencies — from app/status-service/requirements.txt
  5. Run tests — pytest if a test suite exists, skip notice otherwise

Stage 2 — DevSecOps Security Scans

File: .github/workflows/security.yml

Triggers on: push to main, every pull_request targeting main, and a weekly cron (Mondays 06:00 UTC) — vulnerability databases move even when the code doesn't.

All 6 jobs below run in parallel, independent of each other and of Stage 1.

Secrets Detection gitleaks

  1. Checkout — full git history (fetch-depth: 0), not just the diff
  2. Run gitleaks — fails the job on any match; a secret "removed" in a later commit is still in history

SAST — Python bandit

  1. Checkout
  2. Set up Python
  3. Install bandit
  4. Run bandit over app/ — SARIF report generated, then a second pass fails the job on medium/high severity
  5. Upload SARIF to code scanning

SBOM + Dependency Vulnerability Scan Syft + pip-audit

  1. Checkout
  2. Check for requirements.txt
  3. Generate SBOM — Syft, CycloneDX format, uploaded as a workflow artifact
  4. Set up Python
  5. Install pip-audit
  6. Run pip-audit — checks every pinned dependency against known-CVE databases

Container Image Scan Trivy

  1. Checkout
  2. Check for Dockerfile
  3. Build image — docker build from app/status-service/Dockerfile, the exact image that would ship
  4. Scan image with Trivy — HIGH/CRITICAL gate, unfixed findings ignored (nothing to remediate yet)
  5. Upload Trivy SARIF to code scanning

IaC Scan — Terraform tfsec

  1. Checkout
  2. Check for Terraform
  3. Run tfsec — one documented exclusion (aws-iam-no-policy-wildcards) for object/stream-scoped ARNs; every other finding is a real gate
  4. Upload tfsec SARIF to code scanning
  5. Fail on tfsec findings

K8s Manifest Scan kube-linter

  1. Checkout
  2. Check for k8s manifests
  3. Run kube-linter — against every manifest under k8s/
Every job above checks its target path exists before running and skips cleanly if not — safe to land before every piece of the platform exists. The same stages run a second time, in GitLab CI's own syntax, via .gitlab-ci.yml. See the live runs for actual pass/fail history, or the dashboard for current status.

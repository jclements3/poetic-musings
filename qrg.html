Troubleshooting Triage — the four questions, in order

Q1 — Blast radius?

First 120 seconds; scope decides urgency.

kubectl get pods -A | grep -v 'Running\|Completed'
systemctl --failed
kubectl get nodes
df -h

One pod, one user, one host — or everything? Ask a second human. Write the answer down.

Q2 — What changed?

Highest-yield question; run the whole battery.

kubectl get events -A --sort-by=.lastTimestamp | tail -30
kubectl rollout history deployment/<n> -n <ns>
helm history <rel> -n <ns>
git log --oneline --since="24 hours ago"
terraform plan -detailed-exitcode
journalctl --since "-24h" -p warning | tail -40

Something almost always changed. Nothing found usually means the wrong layer, not no cause.

Q3 — Which layer?

Walk the request path, half-split.

dig <name>
curl -v https://<host>/health
kubectl get endpoints <svc> -n <ns>
kubectl get pods -n <ns>
kubectl logs <pod> -n <ns> --previous

DNS → LB → ingress → service → endpoints → pod → app. Start at endpoints, half-split.

Q4 — Fastest safe rollback?

Answer before any fix attempt.

helm rollback <release> -n <ns>
kubectl rollout undo deployment/<n> -n <ns>
git revert <sha> && git push

Stabilize first, root-cause second. If Q2 found the change and a rollback exists, take it.

Rules of engagement, unknown system

  • Read-only first — get/describe/logs/history/status before any mutating verb.
  • Snapshot before touching — kubectl get ... -o yaml > was.yaml · terraform state pull > state.backup.json
  • Log the terminal — script -a /tmp/incident-$(date +%F-%H%M).log
  • One change at a time — change, verify, record, then next.
  • Stop and escalate when the fix touches a security/ATO-boundary config, risks data loss, or 30 min with no hypothesis.

Pipeline is red — decode by stage

  • BUILD fails: read the first error only.
  • TEST fails: rerun once at most — twice-failed is real.
  • SCAN fails, no code change: the CVE database moved.
  • DEPLOY fails: ask what changed on the target, not the repo.

Terraform died mid-apply

terraform plan  # shows exactly what landed
terraform apply -replace=<failed-address>

Plan first — never re-apply blind onto a half-applied state.

Node NotReady — five suspects

systemctl status kubelet
journalctl -u kubelet | tail
df -h
free -m
systemctl status containerd

Everything down vs. one thing down

  • kubectl itself timing out = control plane. Go to the node: crictl ps -a.
  • kubectl fine but services failing = workload layer — back to Q3.

The quiet killer sweep — certificates

echo | openssl s_client -connect <host>:443 2>/dev/null \
 | openssl x509 -enddate -noout
kubeadm certs check-expiration

Date-clustered onset across unrelated services is the tell.

Severity & comms cadence

  • SEV1 — mission service down / security event: status every 30 min.
  • SEV2 — degraded / redundancy lost: hourly.
  • SEV3 — single user / cosmetic: ticket queue.
  • Solo-operator loop: stabilize → communicate → capture → fix → verify → write.

The boring six — check these first

  • 1 recent change · 2 certificate expiry · 3 disk full/inodes
  • 4 DNS · 5 permissions (RBAC/IAM/SELinux) · 6 resource exhaustion

Postmortem, blameless, six fields: impact · timeline · root cause (a condition, never a name) · what worked · what didn't · actions with owner/date.

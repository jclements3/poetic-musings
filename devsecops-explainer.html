The big picture, first

Every DevSecOps tool exists to answer one question at one stage of this pipeline. Code moves left to right; each box is a tool whose only job is to make the next box safer, faster, or more reliable to reach.

Bottom line: this sprint delivered verified, working capability across all nine required areas of that chain — real infrastructure, real security scanning, real identity, real monitoring, real config management — with the honest remaining gaps named rather than glossed over.

Bottom Line Up Front (BLUF)

Infrastructure as Code (Terraform): full environments stand up from code in minutes, verified against a live AWS account. Automated Pipelines (CI/CD)

GitHub Actions CI/CD

CI/CD (Continuous Integration/Continuous Delivery) is automation that builds, tests, and checks code every time it changes, instead of relying on a person to remember to run those checks manually.

Bottom Line Up Front (BLUF)

Bottom line: nothing reaches production without passing the same automated checks every single time — no manual gatekeeping step to forget, and no "it worked on my machine" surprises.

Real, verified at poetic-musings
  • Two real workflow files run on every push/PR to main: ci.yml (Python lint via ruff, unit tests via pytest) and security.yml (a 6-job security pipeline: gitleaks secrets scan, bandit SAST, Syft SBOM + pip-audit dependency scan, Trivy container image scan, tfsec IaC scan, kube-linter Kubernetes manifest scan).
  • Per JOB.html: "Verified on the first real run: it wasn't green — it caught five actual problems, including a live vulnerability in a dependency — and each was fixed for the real reason, not by silencing the alert."
  • The security pipeline also runs on a weekly cron (`0 6 * * 1`) specifically to catch newly disclosed CVEs against code that hasn't changed — not just at commit time.
  • Findings feed GitHub's native code-scanning dashboard via SARIF upload (bandit, Trivy, tfsec), so results are visible in one place rather than eight disconnected tool outputs.
.github/workflows/ci.yml, .github/workflows/security.yml
Jenkins

Jenkins is a self-hosted 'automation server' — a program that watches for code changes and automatically runs a checklist of steps (build, test, scan, deploy) every time someone pushes code, instead of a person running those steps by hand.

Bottom Line Up Front (BLUF)

Bottom line: automating the build/test/deploy checklist means nothing ships without passing the same checks every time, with no step skipped because someone was in a hurry — that's fewer production incidents caused by human error, not a tooling nicety.

Real, verified at poetic-musings
  • Jenkins itself is not installed or used anywhere in this repo — that's a named gap, not something dressed up as experience.
  • The equivalent capability is proven in two comparable tools instead: GitHub Actions (.github/workflows/ci.yml) and a line-for-line GitLab CI mirror (.gitlab-ci.yml) — same concept (automation server watching pushes, running staged checks), different vendor.
  • That pipeline isn't theoretical: the first real run caught 5 genuine failures (an invalid Trivy action version tag, an overly broad lint glob, a real Flask CVE via pip-audit, 6 kube-linter findings, and a tfsec rate-limit failure) and each was root-caused and fixed, not silenced.
  • The transferable concepts — stages, gates, artifacts, fail-the-build-on-a-real-finding — are the same ones a Jenkinsfile expresses in Groovy; the Jenkinsfile-specific syntax itself is unproven here.
.github/workflows/ci.yml, .github/workflows/security.yml, .gitlab-ci.yml
Jenkins: powerful, more setup

Jenkins can do almost anything (any language, any plugin, any custom workflow) because it's a general-purpose server you install and maintain yourself — the tradeoff is you own the setup, upgrades, and plugin security, unlike a hosted service that manages that for you.

Bottom Line Up Front (BLUF)

Bottom line: Jenkins buys maximum flexibility at the cost of ongoing care and feeding (patching, plugin management, server uptime) — the right call when requirements are unusual or on-prem is mandated, the wrong call when a team just needs a pipeline running fast with minimal upkeep.

Real, verified at poetic-musings
  • No Jenkins instance exists in this repo, so its setup/maintenance overhead hasn't been hands-on exercised here — stated plainly rather than implied.
  • What is proven is the 'less setup' side of the same tradeoff: GitHub Actions and GitLab CI are both hosted/managed automation servers, and both pipelines here run with zero server to patch or maintain, wired via committed YAML files.
  • Those pipelines still do real, non-trivial work without a maintained server: 7 layered security gates (gitleaks, bandit, pip-audit, Syft SBOM, Trivy, tfsec, kube-linter) run on every push, catching a real Flask CVE and 6 real Kubernetes hardening gaps.
  • The honest gap: judging Jenkins specifically on plugin-management overhead, upgrade cadence, or agent/executor scaling isn't something this repo can speak to first-hand.
.github/workflows/security.yml, .gitlab-ci.yml
Jenkins vs. Ansible

These solve different problems even though both are 'automation': Jenkins (an automation server) decides WHEN to run a pipeline and orchestrates its stages; Ansible (a configuration-management tool) decides WHAT state a machine should end up in and makes it so, idempotently. A shop commonly uses both together — Jenkins as the trigger/orchestrator, Ansible as one of the steps it calls.

Bottom Line Up Front (BLUF)

Bottom line: don't evaluate these as competitors — Jenkins answers 'did the pipeline run on every change,' Ansible answers 'is the server actually configured correctly right now' — a team missing either one has a real gap, not a redundant tool.

Real, verified at poetic-musings
  • Jenkins itself isn't used in this repo, so this comparison leans on the comparable orchestrator (GitHub Actions / GitLab CI) standing in for Jenkins's role, next to Ansible which IS real and hands-on here — that substitution is named explicitly, not glossed over.
  • The orchestration side is proven: two parallel pipelines (GitHub Actions + GitLab CI) run lint/test then 7 security gates on every push, catching 5 real bugs on first run.
  • The configuration-management side is proven with hard evidence Jenkins-style tools don't produce: a real idempotency test (changed=1 cold, changed=0 warm) showing Ansible converges a system to a known state repeatably.
  • The repo's own README states the distinction directly: 'Terraform answers does the infrastructure exist; Ansible answers is the right software deployed and configured on it, every time, idempotently' — Jenkins/CI answers a third, different question: did every change pass the same automated checks.

Packaging & Orchestration

Docker (packaging)

Docker packages an application together with everything it needs to run — code, dependencies, runtime — into a single portable unit called a container image, so it runs the same way everywhere.

Bottom Line Up Front (BLUF)

Bottom line: "it works on my machine" stops being an excuse — the application runs identically on a developer's laptop, in the test pipeline, and in production because it's the exact same packaged image every time.

Real, verified at poetic-musings
  • app/status-service/Dockerfile is a real, working multi-stage build: stage 1 installs Python dependencies into an isolated prefix, stage 2 copies only the installed packages (not pip/build tooling) into a minimal `python:3.12-slim` runtime image.
  • The image runs as a dedicated non-root user (`app`, uid 10001) with no login shell, and pip/setuptools/wheel are fully removed from the final runtime image to shrink attack surface and eliminate a class of CVEs entirely.
  • A `HEALTHCHECK` is built into the image itself, hitting the app's own `/healthz` endpoint — the container reports its own health, not just "process is running".
  • The pipeline's Trivy container scan actually builds this Dockerfile and scans the resulting image for HIGH/CRITICAL vulnerabilities on every run (.github/workflows/security.yml).
app/status-service/Dockerfile
Dockerfile to running container

A Dockerfile is a text recipe for building an image; running that image produces a live, isolated container — the actual running instance of the application.

Bottom Line Up Front (BLUF)

Bottom line: the exact recipe that builds what runs in production is checked into version control and human-readable, so anyone can see precisely what the running application consists of — no undocumented manual server setup.

Real, verified at poetic-musings
  • The Dockerfile's build instructions are documented inline with real operational reasoning, e.g. why `PROMETHEUS_MULTIPROC_DIR` lives under `/tmp` — "it works under the same read-only-root-filesystem + emptyDir-at-/tmp pattern the rest of this image already relies on".
  • The resulting container is designed for Kubernetes's `restricted` Pod Security Standard: read-only root filesystem, no root user, writes confined to `/tmp` via an emptyDir volume — matching what's actually declared in the k8s manifests (k8s/base/deployment.yaml).
  • Verified, not assumed: this image is what the CI pipeline builds and Trivy-scans (security.yml) and what actually gets deployed and load-checked against a live `kind` Kubernetes cluster (k8s/cis-benchmark/README.md — Deployment rolled out and confirmed `Ready` via `kubectl`).

Docker vs Kubernetes at scale

Docker runs one container at a time on one machine; Kubernetes is the layer on top that runs many containers across many machines, automatically restarting failures, spreading load, and rolling out updates without downtime.

Bottom Line Up Front (BLUF)

Bottom line: Docker alone is fine for one container on one laptop — it's Kubernetes that keeps the application available when a server dies, traffic spikes, or an update is being rolled out, which is what "production at scale" actually requires.

Real, verified at poetic-musings
  • This project uses both, at the layer each is meant for: Docker builds and packages the application (app/status-service/Dockerfile); Kubernetes runs, schedules, and keeps it alive (k8s/base + k8s/overlays for dev/prod via Kustomize).
  • Per JOB.html: "Workloads stay up through a node failure or a rolling update instead of dropping traffic" — enforced via a minimum-healthy-replicas PodDisruptionBudget, default-deny NetworkPolicy with explicit allow rules, and the `restricted` Pod Security Standard (no root, no writable root filesystem).
  • Verified against a real running cluster, not a diagram: `kubectl kustomize k8s/overlays/dev | kubectl apply -f -` actually deployed the Deployment (confirmed `Ready`), Service, both NetworkPolicy objects, and the PodDisruptionBudget, and a kube-bench CIS scan scored the live cluster: 62 PASS / 11 FAIL.
  • Honest gap: the 11 kube-bench failures are named individually as the `kind` (Kubernetes-in-Docker) test cluster's own default control-plane configuration (e.g. `--profiling` left enabled, no audit log configured) — not something this repo's Kubernetes manifests control, and exactly the kind of gap a managed/hardened cluster (EKS/GKE/AKS) would close.

Kubernetes keeps the app running

Kubernetes continuously watches an application's running containers and automatically fixes problems — restarting crashed ones, rescheduling them off a failed machine, and never dropping below a minimum number of healthy copies during an update.

Bottom Line Up Front (BLUF)

Bottom line: the application stays available to users through failures and updates because Kubernetes is actively enforcing that outcome, not because someone is manually watching a dashboard and intervening.

Real, verified at poetic-musings
  • A PodDisruptionBudget enforces a minimum number of healthy replicas through any voluntary disruption (node drain, rolling update) — verified live and confirmed via `kubectl get` against a real cluster.
  • Default-deny NetworkPolicy objects (both confirmed live) mean no pod can talk to another unless explicitly allowed — reducing blast radius if one component is compromised.
  • Pods run under the `restricted` Pod Security Standard: no root, no writable root filesystem — verified via the actual deployed manifests, not just declared intent.
  • Real, scored proof of cluster health: kube-bench CIS benchmark run against the live cluster returned 62 PASS / 11 FAIL / 48 WARN, with every failure individually attributed to the test cluster's own tooling defaults rather than this repo's configuration (k8s/cis-benchmark/README.md).

Infrastructure & Configuration

Terraform: Infrastructure as Code

Terraform lets you describe infrastructure (networks, storage, servers, permissions) as version-controlled text files instead of clicking through a cloud provider's web console — run the same file and you get the same infrastructure, every time, reviewable in a pull request like any other code change.

Bottom Line Up Front (BLUF)

Bottom line: infrastructure defined as code means environments are reproducible, auditable, and stand up in minutes instead of hours of manual console work — and because it's version-controlled, every infrastructure change has a reviewable history, which matters directly for audit and compliance.

Real, verified at poetic-musings
  • Applied for real against a live, personal free-tier AWS account (us-east-2), not just planned: all 33 planned resources (VPC across 2 AZs, ECR, KMS-encrypted S3 buckets, least-privilege IAM role) were created and independently verified with aws ecr describe-repositories, aws ec2 describe-vpcs, aws s3api list-buckets, and aws kms describe-key, then torn down clean with terraform destroy.
  • A real bug was caught by the apply itself, not by static scanning: aws_cloudwatch_log_group.vpc_flow_logs failed with AccessDeniedException because the KMS key had no policy statement granting the logs.<region>.amazonaws.com service permission to use it — a class of error that only surfaces at the live API level, fixed in modules/aws-platform/kms.tf and re-verified with a second apply.
  • Passed automated scanning too: terraform validate clean, and tfsec clean with one documented, justified exclusion (aws-iam-no-policy-wildcards, for object-level ARN suffixes AWS requires) — both wired into CI on every push.
  • The honest limit named up front: the Azure side (azure-platform module) is written and validate-clean but never applied — no Azure subscription was available — which is disclosed rather than blended in with the proven AWS results.
infra/terraform/README.md, infra/terraform/modules/aws-platform/kms.tf
Terraform workflow

Terraform's normal workflow is three steps: init (download providers, set up state), plan (show exactly what will change, before touching anything), apply (make the change) — the plan step is the safety net that lets a human review an infrastructure change before it happens, the same way a code review happens before a merge.

Bottom Line Up Front (BLUF)

Bottom line: the plan-before-apply workflow is a built-in review gate — no infrastructure change happens as a surprise, because the exact diff is shown and can be reviewed or blocked before it's real, cutting the risk of an unreviewed change taking down production.

Real, verified at poetic-musings
  • The real workflow used here: terraform init, then terraform plan -var-file=environments/dev/terraform.tfvars, then terraform apply with the same var file — one root module reused across environments/dev and environments/prod tfvars, so dev and prod can't silently drift out of sync from duplicated code.
  • State strategy is deliberately not local: the intended backend is S3 (versioned, SSE-encrypted) plus DynamoDB for locking, documented in backend.tf and left commented out specifically so terraform init/validate work without needing pre-existing AWS infrastructure just to test the code.
  • The workflow caught a real problem that plan/validate alone would have missed: the apply step surfaced an AccessDeniedException on the KMS key for CloudWatch Logs that neither terraform validate nor tfsec flagged, because nothing in the HCL syntax itself was wrong — only the live API rejected it, which is the actual argument for running apply at least once rather than trusting static checks alone.
  • tfsec runs as an automated CI gate on every push (.github/workflows/security.yml), so the plan/apply discipline used by hand here is backed by the same static check running automatically on every future change, not just when someone remembers to run it.
infra/terraform/README.md, infra/terraform/backend.tf, .github/workflows/security.yml

Bottom Line Up Front (BLUF)

Bottom line: knowing Terraform doesn't mean the whole HashiCorp ecosystem is covered — secrets management (Vault) in particular is a named, real gap here, worth knowing about before assuming 'HashiCorp experience' means everything's handled.

Real, verified at poetic-musings
  • Terraform itself is proven hands-on here: a real AWS apply, a real bug fix, a real teardown (see the Terraform Infrastructure as Code card) — that's the one HashiCorp tool with genuine, verified experience in this repo.
  • Vault (HashiCorp's secrets manager) is not used anywhere in this repo — the Ansible README states this directly as a named gap: 'No secrets/vault usage. Nothing sensitive is configured by this playbook... a real gap if this were managing anything with actual credentials.'
  • Consul and Nomad are not present in this repo at all — no service mesh or HashiCorp-native scheduler has been built or exercised here, stated plainly rather than implied by adjacency to Terraform.
  • What IS proven adjacent to secrets-handling: encryption at rest is used throughout the Terraform layer itself (KMS-encrypted S3, customer-managed KMS key with rotation for ECR) — real secrets-adjacent security discipline, just not via HashiCorp Vault specifically.

HashiCorp's infrastructure toolkit

HashiCorp's tools are designed to compose: Terraform provisions the infrastructure a workload runs on, Vault would manage the secrets it needs to run, Consul would let services find and securely talk to each other, Nomad would schedule the workloads themselves — each one solves a distinct layer of the same overall infrastructure problem.

Bottom Line Up Front (BLUF)

Bottom line: this repo demonstrates the provisioning layer of that toolkit end to end on real infrastructure, with the other layers (secrets, service mesh, scheduling) named as clear, honest next steps rather than claimed as already covered.

Real, verified at poetic-musings
  • The provisioning layer is real and layered correctly with the rest of the stack: Terraform provisions account-level primitives (network, registry, storage, keys, IAM); Kubernetes deploys onto that; Ansible configures software on top of it; the CI pipeline's tfsec gate checks the Terraform on every push — 'provisioning, config management, and policy enforcement as three distinct, cooperating layers,' per the repo's own JOB.html description.
  • Encryption/key-management concepts that Vault would formalize are already present, just handled directly in Terraform: KMS-encrypted S3 artifact bucket, AES256-encrypted access-log bucket, customer-managed KMS key with automatic rotation for ECR image encryption — real security discipline, without the dedicated secrets-management tool.
  • Service-mesh/networking discipline that Consul would formalize is partially present via Kubernetes NetworkPolicy instead: a default-deny policy plus explicit allow rules, verified on a real running kind cluster and CIS-benchmark scanned (62 pass / 11 fail, failures named individually with cause).
  • Nomad-style scheduling is out of scope entirely here — Kubernetes is the scheduler in use, and that substitution (Kubernetes instead of Nomad) is a deliberate, reasonable choice worth being able to explain, not an unstated gap.

Ansible

Ansible is a configuration-management tool: once a server or container exists, Ansible answers a different question than 'does it exist' — it makes sure the right software is installed and correctly configured on it, and keeps re-checking that every time it runs, without needing an agent installed on the target.

Bottom Line Up Front (BLUF)

Prometheus

Prometheus is a tool that constantly asks every system 'are you healthy and how busy are you right now?' and keeps a timestamped history of the answers.

Bottom Line Up Front (BLUF)

Bottom line: Prometheus turns 'the app feels slow' into 'p95 latency on /checkout jumped from 80ms to 900ms at 2:14pm' — the difference between guessing at an outage and diagnosing it in minutes.

Real, verified at poetic-musings
  • A real status-service exposes Prometheus-format metrics at /metrics, and a real Prometheus instance scrapes them every 5 seconds (observability/README.md).
  • Two metrics are tracked deliberately, not just enabled by default: http_requests_total (a Counter) and http_request_duration_seconds (a Histogram used for the p95-latency panel).
  • A real bug was caught during development: gunicorn ran 2 worker processes, and Prometheus's default in-process registry only saw whichever worker handled a scrape, silently undercounting real traffic by roughly half (30 requests showed as only ~13-17).
  • Fixed with Prometheus's documented multiprocess mode (PROMETHEUS_MULTIPROC_DIR + MultiProcessCollector), then re-verified three separate ways — the raw /metrics endpoint, Prometheus's own query API, and Grafana's datasource-proxy — all agreeing on the same number (30 of 30).

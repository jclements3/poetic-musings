This Playbook is a 9-zone DevSecOps reference — Plan & Source through Evidence & Govern — built around haskell.py, a real, working functional-programming toolbox written in point-free Python. It exists so poetic-musings can be the reference implementation: the place a reusable DevSecOps toolchain gets proven once, honestly, instead of rebuilt from scratch on every future project. To be clear about where it stands today: this is the toolbox's first real home, not a track record. Why functional / point-free Python, for DevSecOps specifically

DevSecOps scripting is mostly parsing untrusted, semi-structured text (requirements.txt, SARIF, lockfiles, scan output) and then deciding something (pass, fail, waive, escalate) based on what's in it — and that combination is exactly where imperative Python gets fragile: nested try/except blocks around every network call and file read, ad hoc string-splitting that breaks the first time a tool changes its output format, and policy logic that's tangled up with I/O so it's hard to test without mocking half the world. Point-free composition and Maybe/Either monads push error handling into the return type instead of scattering it across exception handlers, so a parser or a gate either produces a value or explains why it didn't, uniformly, without a caller ever forgetting to catch something. Parser combinators let you build a SARIF or requirements.txt reader out of small, composable pieces instead of a wall of regex that silently misparses an edge case. And because the core functions are referentially transparent — same input, same output, no hidden state — they're trivially unit-testable: feed a scanner function a fixture, assert on the Either it returns, no live scan required. None of this is FP for its own sake; it's picking the tool that matches the actual shape of the problem: composing small, honest, testable steps over a pipeline of untrusted input.

The Toolbox — haskell.py

A from-scratch Haskell-style functional core for Python: point-free combinators (compose/pipe, curry, foldl/foldr/scanl), a Maybe via a falsy NOTHING sentinel, an Either via Ok/Err tuples, do-notation for both, parser combinators, and monoids — zero external dependencies. Nine scripts are built on top of it, each one importing nothing but from haskell import ..., meant to be dropped into the next project standalone.

# deps.py — a real requirements.txt parser built entirely from haskell.py combinators
name    = rx(r"[A-Za-z0-9][A-Za-z0-9._-]*")
op      = rx(r"==|~=|>=|<=|!=|<|>")
version = rx(r"[A-Za-z0-9.*+!_-]+")

@doP
def spec():
    f = yield op
    v = yield version
    return f + v

@doP
def req():
    n  = yield name
    _  = yield opt(extras)
    ss = yield sepBy(spec(), lit(","))
    return (n, ss)

The 9 Zones — why each matters to the reference-implementation vision

1 — PLAN & SOURCE

The first zone sets the standard the rest of the playbook has to live up to: if source and dependency intake aren't handled consistently here, nothing built on top of it in future projects will be either. This is where the reference implementation earns the right to be reused.

2 — DEVELOP

Development-time checks are where the FP toolbox pays off first — small, composable, testable functions that a developer can run locally before anything hits CI, so the same logic that gates a pipeline later is already familiar and trusted.

3 — BUILD

A poster-child implementation has to prove its build step is reproducible and inspectable, not just green — this zone is where 'it built' gets replaced with 'it built, and here's exactly what's in it,' the standard every future project should inherit by default.

4 — TEST

Testing is where referential transparency stops being a talking point and becomes the reason the toolbox itself is crediblely testable — if haskell.py's own combinators aren't well-tested, nothing built on top of them can be trusted either.

5 — SECURE

This is the zone most likely to get reused verbatim in a future project: composable scanners and Either-typed triage logic mean a new codebase can plug into the same gating rules instead of every project inventing its own ad hoc policy script.

6 — PROVISION

Provisioning ties the playbook back to real, verified infrastructure (Terraform, Kubernetes) rather than leaving it as a scripting exercise — the reference implementation only matters if it stands up something real.

7 — DEPLOY & ORCHESTRATE

Deploy and orchestrate is where the playbook has to survive contact with three real pipeline vendors (GitHub Actions, GitLab CI, Jenkins) — proving the toolbox isn't tied to one CI system is what makes it actually portable to the next project.

8 — OPERATE & OBSERVE

A reusable standard has to outlive the initial build; this zone is the honest test of whether the toolbox's outputs are still useful once the pipeline is running unattended, not just on day one.

9 — EVIDENCE & GOVERN

Evidence and governance is the zone that keeps every other claim on this page honest — traceable, re-checkable artifacts are what let 'reference implementation' mean something more than a label.

Honest Gaps

  • haskell.py has zero unit tests. Every function used by the 8 downstream scripts is exercised indirectly, but roughly 150 other combinators (streams, containers, strings) are untested.
  • Not wired into live CI yet. playbook/ is a standalone toolbox — ci.yml/security.yml/the Jenkins pipeline still run their scanners directly, unchanged.
  • sbom_diff.py only verified against demo fixtures — no syft in this environment to produce a real SBOM to diff.
  • 21 unpinned GitHub Actions, found and left unfixed — a real, legitimate follow-up, out of scope for this integration pass.
  • The generic-secret regex has a real false-positive class (keyword + quoted string ≥12 chars, blind to literal-vs-variable) — scoped around here, not fixed in the regex.

The Pitch

poetic-musings started as an eclectic hobby repo — hardware, music, FPGA work — and that's actually part of the pitch: it's a real, messy, lived-in codebase, not a sanitized demo built to look good in an interview. What makes it a credible poster child isn't that everything in here is finished or battle-tested — it isn't, and I'd rather tell you that up front than have you find the gaps yourself. It's that everything marked verified actually is: a live Terraform apply, a hardened Kubernetes cluster, a real STIG scan with the fail count shown next to the pass count, three CI vendors running the same pipeline and catching real vulnerabilities. Now I'm carrying that same discipline into a reusable toolbox — haskell.py, a genuinely working point-free FP library for Maybe/Either error handling and parser combinators — because the scripting problems in DevSecOps are exactly the kind FP is good at: parsing untrusted structured text and making policy decisions you can actually test. It's brand new here, being integrated and re-verified right now, not something I'm claiming has years of mileage. But the plan is straightforward: prove it here first, on a real repo with real gaps named plainly, and then carry this exact toolbox and this exact standard of honesty into every project after this one.

Roadmap

  1. Wire playbook/ scripts into the live GitHub Actions, GitLab CI, and Jenkins pipelines as a fourth verification layer, not just a standalone toolbox run by hand
  2. Add a property-based test suite for haskell.py itself using Hypothesis, so the combinators are verified the same way the rest of the repo insists everything else be verified
  3. Extract playbook/ as its own versioned package once a second real project needs it, rather than copy-pasting it forward
  4. Quarterly re-audit of the 9 zones against MASTER-PLAYBOOK.md's own scope statement, to keep the 'reference implementation' claim honest as the repo evolves
  5. Replace remaining ad hoc parsing in existing scripts (cve.py, sbom_diff.py, deps.py) with haskell.py parser combinators one file at a time, tracked as visible progress rather than claimed all at once
  6. Publish a short honest changelog of what in the playbook moved from 'integrated' to 'verified in production use' each quarter

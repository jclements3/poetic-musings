Likely follow-up #1: “Tell me about that AI code generation experience — what burned you?” — LONG version

The failure mode, specifically: over about 9 months, using a top-tier AI coding subscription, I repeatedly tried to have AI port working code between languages — C# to Rust, Python to Rust — on physics/GNC simulation code where correctness is the entire point. Every time, the ported code looked plausible and compiled, but the covariance matrix math was wrong. Not once — repeatedly, across many attempts over that period. The AI could not reliably preserve the actual mathematical semantics across the language port; it could produce code that read correctly without being correct.

How it was caught: not by trusting the output — by independent verification against the original. Property-based testing against the known-good source implementation, function by function, failed. Unit testing failed. Only visual inspection by a SME caught the bug. If I had merged on “it compiles and looks right,” the errors would have shipped silently into a simulation whose whole value is numerical correctness.

The concrete change: I don’t trust AI-generated code translated from a working implementation in another language without independently verifying it against that original, the same rigor I’d apply to any safety- or correctness-critical port regardless of who or what wrote it. AI-assisted code gets the same test/verification gate as anything else — arguably a stricter one, since a fluent, confident-looking wrong answer is a specific new failure mode a human developer is less likely to produce. AI is like a junior developer with suboptimal and misleading test results (like happy pass tests).

Why this matters for the role: AI-generated code entering a pipeline is a real, current DevSecOps risk — same category as an unvetted dependency, just a newer one, and I’ve hit its actual failure mode firsthand, not hypothetically. The gate discipline is the same instinct as the Terraform/STIG root-cause work below: don’t trust that something is right because it looks right — verify it independently, and this is exactly the emerging security surface a DevSecOps practice needs to account for as AI-assisted development spreads.

Likely follow-up #2: “Walk me through that Terraform/STIG catch in more detail.” — SHORT version

Terraform: A Jenkins build passed every gate — lint, tests, secrets scan, SAST, SBOM, dependency scan, container scan — then failed on the IaC stage. trivy config caught a real CRITICAL: a storage account in the Terraform with no network rules block, so it defaulted to public access. The same commit had already passed GitHub Actions’ tfsec scan clean — tfsec simply has no rule for that misconfiguration class. Same code, two tools, two different verdicts. Lesson: a passing scan proves that tool found nothing, not that nothing’s wrong — which is why I don’t sign off on a single tool’s “clean.”

STIG: A real DISA STIG scan against a RHEL8 image came back 51 failures out of 409 rules evaluated. Instead of treating that as 51 problems, I root-caused them into three buckets — PAM/password policy, crypto policy, RPM package integrity — each traceable to one root cause: a vendor base image ships unopinionated defaults on purpose, because those are site-specific hardening decisions, not vendor bugs. The scan’s value isn’t “the image is broken,” it’s “here’s exactly which rules the hardening pass has to touch.” Same root-cause instinct I’ve used in FRACAS for 20 years, just pointed at a security scan instead of a hardware failure report.

Likely follow-up #2: “Walk me through that Terraform/STIG catch in more detail.” — LONG version

Terraform / CRITICAL misconfig, real and verifiable in this repo (course/book/chapter-03-build-and-test.md §4, Jenkins build #7):

  • Jenkins build #7 of the devsecops-pipeline job ran a full gate: lint, test, secrets scan, SAST, SBOM, dependency scan, container scan — all passed clean — then failed at the IaC scan stage.
  • trivy config (Aqua’s actively-maintained successor to tfsec, which was archived by its own maintainer) flagged a real CRITICAL finding: infra/terraform/modules/azure-platform/main.tf:23-51 — an azurerm_storage_account resource with no network_rules block, so the implicit default action is Allow — public network access to the storage account by default.
  • The catch, specifically: the same commit, same target directory, was also scanned by tfsec in the GitHub Actions pipeline — and tfsec didn’t flag it. Its Terraform-only, narrower ruleset simply doesn’t have a rule for this misconfiguration class. Two tools, same input, different results — and the narrower one was the one wired into the “official” pipeline.
  • The lesson to state out loud: tool coverage is not uniform, and a passing scan from one tool is not proof of security — it’s proof that tool’s specific ruleset found nothing. That’s why the gate needs the actively-maintained, broader-coverage tool, and why a real finding was left in place rather than quietly fixed — the failed build IS the evidence the gate works.

STIG / 51-of-409 root cause, real and verifiable (chapter-05-secure.md):

  • Real OpenSCAP DISA STIG scan against a RHEL8 image, 409 rules evaluated in-scope (1,163 more correctly excluded as not-selected for that profile). 51 failed. I root-caused all 51 into three categories instead of treating them as 51 separate problems:
    1. PAM password/account policy (pam_faillock, pam_pwquality, etc.) — root cause: base OS images ship PAM in vendor-default configuration, because password-complexity policy is site-specific and can’t be baked in by a vendor. Verify with cat /etc/security/pwquality.conf.
    2. Crypto policy (SSH cipher/MAC hardening) — root cause: RHEL’s system-wide crypto policy defaults to general-compatibility, not DISA_STIG. Verify with update-crypto-policies --show; fix is update-crypto-policies --set DISA_STIG — one command, but it changes what ciphers the whole box negotiates, so it’s not something to run blind on a box with live traffic.
    3. RPM package integrity (rpm_verify_hashes, gpgcheck_local_packages) — root cause: package-manager-level integrity verification isn’t enforced by default. Verify with rpm -Va and check gpgcheck=1 in /etc/dnf/dnf.conf.
  • The point to make explicitly: none of these 51 are bugs in the base image — a minimal, unopinionated OS image doing minimal, unopinionated things is correct vendor behavior. A STIG scan’s value isn’t telling you the image is broken, it’s telling you exactly which rules a hardening pass has to touch, by rule ID, instead of guessing. That’s the root-cause-analysis instinct from decades of IV&V/FRACAS work, applied to a security scan instead of a hardware failure report.

“Tell me about a time you led a team” — LONG version

How it started: a single ask — “we need IV&V for the GMD-RKV interceptor, about 1.5 FTE.” No process, no team, no budget line beyond that.

What I built it into: I grew that into a 17-person team, and — more important than the headcount — I built and formalized the actual management model underneath it, which I wrote up and presented as a paper: “Moneyball IV&V.” By the time I was GME-S IV&V Deputy, the scope had grown to all of GMD — Ground Systems, Booster, Redesigned Kill Vehicle, Exo-atmospheric Kill Vehicle — a $22 million annual budget across 13 companies and 7 contract vehicles, plus two labs and new facility development.

The innovation, specifically — the Moneyball IV&V model: the paper’s core argument, borrowed directly from the Moneyball baseball analogy: stop buying activities, start buying outcomes. Traditional IV&V cost estimates are Level-of-Effort — hours against a Scope of Work — with no real answer to “after the funding’s spent, is the fielded software better?” Moneyball IV&V reduces the whole management challenge to one number: Defect Removal Efficiency (DRE), a predictive cost model anchored to Capers Jones’ dataset of 26,000 other software development efforts. Instead of status reports saying “continuing to look at this,” stakeholders get weekly graphs of planned versus actual defects removed. It’s the same shift as in-phase, distributed Agile IV&V generally: assess alongside development as it happens, not after a phase is already done, and make the value objectively visible every week instead of asserted.

Proof it worked, not just my opinion of it: MDA Letter of Recognition for Innovative Agile IV&V on the Redesigned Kill Vehicle in 2017, and again for GME-S more broadly in 2018 — the same innovation recognized two years running by the customer, not just internally. Plus MDA Individual and Best Team Recognition in 2019. I also formally presented the Moneyball IV&V paper and model to the organization, not just used it quietly — it was built to be replicated, with every equation and input documented so other stakeholders could run it themselves.

The model is also what kept the budget alive. In a budget drill I was asked, “What if your budget was cut by $1 million?” Because the model predicts defect removal as a function of funding, I didn’t answer with opinion — I answered with a number: here’s how many additional defects go unremoved and get fielded instead, quantified. I could run the same model forward too — given 3 months of funding, here’s the predicted number of SEV-1 defects that funding level would actually catch versus miss. That’s the entire point of reducing IV&V to a single defensible metric: when someone asks to cut the budget, you don’t have to argue feelings against their spreadsheet — you have your own spreadsheet, and it’s the reason the funding kept getting approved.

What made it a “great team,” not just a bigger budget: I designed and taught the leadership and technical training myself — assessment tools and techniques, team building, how to communicate a controversial defect finding without the room shutting down, effective technical writing. I trained junior staff, balanced staffing across efforts, and mentored people on MBSE and Design Structure Matrix system-architecture assessment. The measure I actually care about: people I trained into that process are still running high-performing Agile IV&V teams on GMD today, well past when I moved on to other roles.

I have not solved the underlying problem — I don’t currently have a testing method that reliably catches this class of AI-introduced error other than SME inspection. Admitting I haven’t solved it is more credible than a neat failure-with-a-bow-on-it story — and it sets up a legitimate question back to the interviewer: how is their team handling AI-generated code verification, because it’s a live problem, not a solved one.

“What would you do if…” — probable situational questions

Terse answers, grounded in real experience and this repo’s own playbook (playbook/MASTER-PLAYBOOK.md) where relevant — not generic DevSecOps platitudes.

“…a security scan blocks a release the team says is urgent?” Check the finding first — is it real or a false positive. If real, it doesn’t ship; a deadline doesn’t override a CRITICAL. If there’s a genuine business case for accepted risk, that’s a waiver — documented, with an expiry and a compensating control, not a silent override. Same discipline as breakeven analysis on IV&V: quantify the risk, don’t just feel it.

“…two scanning tools give conflicting results on the same code?” Real example, not hypothetical: tfsec passed a Terraform misconfig that trivy config caught as CRITICAL on the same commit. A pass from one tool proves that tool’s ruleset found nothing — not that nothing’s wrong. Trust the broader/actively-maintained tool, and treat a narrower tool’s silence as absence of evidence, not evidence of absence.

“…you inherit a pipeline with no tests and years of legacy code?” Don’t try to boil the ocean. Root-cause and categorize first — same method as the STIG 51-failure triage: group failures into a handful of underlying causes instead of fixing 500 symptoms one at a time. Gate new code immediately; backfill coverage on the legacy code by risk, highest-blast-radius modules first.

“…a developer pushes back that a finding is a false positive?” Don’t argue from authority — verify. If they’re right, fix the rule/exclude it with documentation of why. If they’re wrong, show them the evidence, not just the tool’s opinion. This is the same “cooperative-adversarial” relationship-building from decades of IV&V — the goal is a correct answer both sides can defend, not a win.

“…you find a critical vulnerability already in production?” Assess blast radius and severity first — that drives the timeline, not panic. Contain if actively exploitable, patch, verify the fix, then root-cause how it got past the gate in the first place and close that gap too — fixing the instance without fixing the gate just guarantees a repeat.

“…leadership wants to skip the security gate to hit a deadline?” Make the risk visible and quantified, in writing, and let leadership make an informed, accountable decision — that’s the waiver process, not a private compromise. I’ve run IV&V panels for milestone reviews; the job is surfacing risk clearly, not personally absorbing the decision to accept it.

“…you’re asked to review AI-generated code before it merges?” Same gate as anything else, arguably stricter — I’ve been burned by exactly this (see the AI code generation story above): AI can produce code that compiles and looks right while being subtly, confidently wrong. Verify against the original/spec independently; don’t let fluency substitute for correctness.

“…you join a team or program with no real DevSecOps culture yet?” Same playbook as standing up an Agile IV&V process across a dozen-plus companies: define the gate, get the tooling running end-to-end even minimally, prove it can actually fail on a real finding (a gate that never fails isn’t trusted), then expand coverage from there. Culture change follows a working, visible process — it doesn’t precede it.

Story Bank — likely follow-ups

“Tell me about yourself” — primary answer

I started working the technical side of DevSecOps when I designed and procured $1.2 million of computer equipment for the Missile Logistics Center — 1,531 users, 8 Sperry supercomputers, and I ran the cables, updated the software, automated tasks, ran backups, and did user support myself.

I then transitioned into the “catch bugs quickly IV&V” DevSecOps zone — unit testing, property-based testing, formal methods testing, using automated tools to find bugs and vulnerabilities.

Long version

After IV&V, I focused on security as the Chief Engineer on AMRDEC’s DARPA SAFE secure-computing program — formal verification with machine-assisted proofs cut security vulnerabilities 95% — a custom hardware/software architecture that defeats the top 25 cyber-attacks out of the box. During this time I acquired my CISSP and other certs.

Then I had the opportunity to focus on the DevSecOps cultural zone as the GMD RKV Software Deputy. I built AGILE style cooperative-adversarial relationships between developers, testers, quality assurance, customers, and management — presenting problems, solutions, and paths forward, not just findings. I’ve done penetration testing, software IV&V, and lab planning through procurement, installation, and operations — up to a $22 million annual budget across 13 companies and 7 contract vehicles.

Finally, I transitioned to Valkyrie’s Artificial Intelligence Lead and worked on tools to reverse engineer binaries for NASIC using AI. Developed prototypes for the Army Corps of Engineers to use drones to detect cracks in dams and bridges. Worked on the RiPPiTT (Rapid Parametric Prototypes Threat Tool) simulations in a DevSecOps environment — demonstrated at the SMD conference. Got really burned with AI code generation and have many lessons learned as the world replaces junior software developers with AI. As DevSecOps evolves, this experience will come in handy.

Currently I’m working on an IRAD FPGA product for the test ranges with a complete DevSecOps pipeline and a customized dashboard. That pipeline is what caught a CRITICAL Terraform misconfiguration a standard scanner missed, and root-caused why 51 of 409 STIG controls were failing on a RHEL image instead of just reporting the count. With this pipeline in place I can focus on the core signal processing FPGA hardware and software.

“That AI code generation experience — what burned you?”

Over about 9 months I repeatedly used a top-tier AI coding assistant to port working physics/GNC simulation code between languages — C# to Rust, Python to Rust. Every time, the ported code compiled and looked right, but the covariance matrix math was wrong. Property-based testing and unit testing both missed it — only a subject-matter expert’s visual inspection actually caught the bug. So now AI-generated code gets the same verification gate as anything else — arguably stricter, since a fluent, confident, wrong answer is a failure mode a human reviewer is less likely to catch by eye.

Long version

The failure mode: the AI could not reliably preserve the actual mathematical semantics across the language port; it could produce code that read correctly without being correct — repeatedly, across many attempts over months.

How it was caught: not by trusting the output. Property-based testing against the known-good source, function by function, failed. Unit testing failed. Only visual inspection by a SME caught the bug.

The concrete change: I don’t trust AI-generated code translated from a working implementation without independently verifying it against the original — the same rigor as any safety- or correctness-critical port. AI is like a junior developer with misleading, happy-path test results.

Why it matters: AI-generated code entering a pipeline is a real, current DevSecOps risk — same category as an unvetted dependency, just newer, and I’ve hit its actual failure mode firsthand.

“Walk me through that Terraform/STIG catch.”

Terraform: a Jenkins build passed every gate — lint, tests, secrets, SAST, SBOM, dependency scan, container scan — then failed on IaC. trivy config caught a CRITICAL that tfsec passed clean on the same commit — tfsec simply has no rule for that misconfig class. A passing scan proves that tool found nothing, not that nothing’s wrong.

STIG: a real DISA STIG scan came back 51 failures of 409 rules. I root-caused all 51 into three buckets — PAM/password policy, crypto policy, RPM integrity — instead of treating them as 51 separate problems.

Long version

trivy config (Aqua’s successor to tfsec, which was archived by its maintainer) flagged infra/terraform/modules/azure-platform/main.tf:23-51 — an azurerm_storage_account with no network_rules block, defaulting to public access. Same commit, same directory, tfsec’s narrower ruleset missed it entirely.

STIG root causes: (1) PAM ships vendor-default because password policy is site-specific — check /etc/security/pwquality.conf. (2) Crypto policy defaults to general-compatibility, not DISA_STIG — update-crypto-policies --set DISA_STIG fixes it, but changes ciphers for the whole box. (3) RPM integrity isn’t enforced by default — check rpm -Va and gpgcheck=1.

None of the 51 are bugs in the base image — a minimal, unopinionated image is correct vendor behavior. The scan tells you exactly which rules a hardening pass has to touch, by rule ID, instead of guessing.

“Tell me about a time you led a team.”

It started with one sentence: “We need IV&V for the GMD-RKV interceptor, about 1.5 FTE.” I grew that into a 17-person team and a defensible, metrics-driven IV&V process, and wrote and presented a paper on the model: “Moneyball IV&V” — stop buying activities, start buying outcomes. Reduces the whole management problem to one number, Defect Removal Efficiency, anchored to real data from 26,000 software projects.

That process took the effort to a $22M annual budget across 13 companies and 7 contract vehicles, and earned MDA Letters of Recognition for Innovative Agile IV&V two years running.

Long version

The innovation: traditional IV&V is Level-of-Effort with no answer to “is the fielded software actually better?” Moneyball IV&V gives stakeholders weekly graphs of planned vs. actual defects removed instead of status-report adjectives.

Proof it worked: MDA Letter of Recognition for RKV (2017) and GME-S (2018), plus MDA Individual/Best Team Recognition (2019). The model was formally presented, not used quietly — every equation documented so others could run it.

The model kept the budget alive: asked in a budget drill “what if your budget was cut $1M,” I answered with a number — how many defects go unremoved and fielded instead. I could run it forward too: given 3 months of funding, the predicted SEV-1 defects that funding would catch vs. miss.

What made it a great team: I designed and taught the leadership/technical training myself, mentored on MBSE and DSM assessment. People I trained are still running high-performing Agile IV&V teams on GMD today.

“Tell me about a time you failed.”

The C#/Rust and Python/Rust physics simulation port. Nine months, a top-tier AI coding assistant, and I still could not get AI-generated ports to reliably preserve the covariance matrix math. I never solved it — that’s the honest answer, not a tidy story with a fix at the end. What I do have is the discipline that came out of it: I don’t trust an AI-assisted language port without independent verification against the original, because I’ve proven to myself firsthand how convincingly it can be wrong.

Long version

Why it was a real failure: not one bug found and fixed — months of repeated attempts against the same problem, never cracked. Property-based testing missed it, unit testing missed it. Only SME visual inspection caught the errors every time — a stopgap, not a real solution.

What I did with it: stopped trusting AI-generated language ports as a shortcut, full stop. I have not solved the underlying problem — no testing method reliably catches this class of error other than SME inspection, and I’m honest about that gap.

Why tell an interviewer this instead of a safer story: it’s real, current, unresolved, and directly relevant to a role where AI-assisted development is only getting more common. It also sets up a legitimate question back to them: how does their team handle AI-generated code verification?

“What would you do if…” — situational questions

…a security scan blocks an urgent release?

Check the finding first — real or false positive. If real, it doesn’t ship; a deadline doesn’t override a CRITICAL. A genuine accepted-risk case needs a documented waiver with expiry and a compensating control, not a silent override.

…two scanning tools disagree?

Real example: tfsec passed a misconfig trivy config caught as CRITICAL, same commit. A pass proves that tool found nothing — not that nothing’s wrong. Trust the broader, actively-maintained tool.

…you inherit an untested legacy pipeline?

Don’t boil the ocean. Root-cause and categorize first, same as the STIG triage — group into a handful of causes, not 500 symptoms. Gate new code immediately; backfill legacy coverage by risk.

…a developer disputes a finding?

Don’t argue from authority — verify. If they’re right, fix or exclude the rule with documentation. If wrong, show evidence, not the tool’s opinion. Cooperative-adversarial: a correct answer both sides can defend.

…you find a live production vulnerability?

Assess blast radius and severity first — drives the timeline, not panic. Contain if exploitable, patch, verify the fix, then root-cause how it got past the gate and close that gap too.

…leadership wants to skip the gate for a deadline?

Make the risk visible and quantified in writing; let leadership make an informed, accountable decision — that’s the waiver process, not a private compromise. Surface risk clearly; don’t personally absorb the decision.

…you review AI-generated code pre-merge?

Same gate as anything else, arguably stricter — I’ve been burned by exactly this. AI can produce code that compiles and looks right while being subtly, confidently wrong. Verify against the spec independently.

…no real DevSecOps culture exists yet?

Same playbook as standing up Agile IV&V across a dozen-plus companies: define the gate, get tooling running end-to-end, prove it can actually fail on a real finding, then expand. Culture follows a working process.

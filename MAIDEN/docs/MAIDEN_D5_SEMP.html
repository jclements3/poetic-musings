How the hardware and software tracks merge

Hardware-in-the-loop

Ingest and fusion run against surrogate .ch10 files in Phase 0, then against bench Station 1 with recorded radar IF and looped video. Every commit replays the same HIL set (SW-005).

Digital twin

A scripted Sportsman flight model drives synthetic az/el and Doppler for all three stations plus a synthetic 6-DOF truth log (SW-004), so fusion and scoring are exercised months before the first instrumented flight. Design in D6 Design.

Hardware sprints

Radar front end, horn, and enclosure iterate through breadboard and 3D-printed versions; Station 1 is bench-tested first, then replicated to three.

Tailoring for one person

Formal artifacts reduce to the nine documents in D0 Index, a requirements spreadsheet with traceability columns, a CI pipeline, and a short self-review at each milestone.

Configuration management

  • One Git repository: firmware/, software/, hardware/ (CAD, schematics, BOM), docs/ (this set), config/ (TMATS templates, calibration files).
  • Tags v0.1-basic-plan, v0.2-prototype, v1.0-field-demo; documents and code release together.
  • Hardware configuration: each station has a serial (MAIDEN-STA-001…003) recorded in its TMATS; calibration files are versioned per serial.
  • Data: every field session gets a directory named by date; raw .ch10 is never modified; derived products are regenerable from raw + tagged code.
  • Change control: a requirement change is a commit to D2 SyRS + RTM with the affected D6/D7 rows updated in the same commit.
